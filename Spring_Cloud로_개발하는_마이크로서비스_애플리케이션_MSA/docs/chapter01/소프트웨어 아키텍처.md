
## 소프트웨어 아키텍처

**소프트웨어 아키텍처란 무엇인가?**
소프트웨어는 1개 이상의 구성 요소들이 존재합니다. 구성 요소는 하나의 모듈, 서비스, 함수라는 단위로 표현 할 수 있습니다. 이러한 **구성 요소들이 다른 구성 요소들과 관계를 맺고 어떻게 사용되는지 정의한 것**이 **소프트웨어 아키텍처(Software Architecture)** 입니다.

**아키텍처(Architecture)의 관점**
프로젝트에 참여하는 이해관계자들은 시스템을 이해하는 관점(View)이 모두 다릅니다. 대표적으로 **Logical View, Implementation View, Process View, Deployment View** 와 같은 뷰가 존재합니다. 이러한 뷰만이 아닌 이해관계자가 많을수록 더욱 다양한 뷰가 존재합니다.
이해 관계자들끼리 원할한 소통을 위해서 **UML(Unified Modeling Language)** 이라는 용어를 사용합니다. UML은 프로그래밍적인 언어가 아닌 관계자들끼리 소통하기 위한 도구입니다.

**아키텍처의 역할**
아키텍처는 코드와 같은 무형의 지식 집합체입니다. 기능적인 측면보다는 전체적인 안정적인 운영을 위해서 구조를 설계하기 위해서 사용됩니다. 아키텍처는 프로젝트 스폰서, 개발자, 대표 사용자, 테스터, 프로젝트 관리자와 같은 이해관계자들과 소통하며 결과물을 설계합니다. 즉, 아키텍처의 역할은 시스템의 구조를 설계하는 역할입니다.

**아키텍처의 스타일과 패턴**
아키텍처의 스타일에 따라서 시스템의 결과도 달라질 수 있습니다.  예를 들어 어떤 한 문제를 해결하는 방식으로 메시지를 보내서 해결할 수도 있고, 이벤트 핸들링하여 해결할 수 있습니다. 이는 아키텍처의 스타일에 따라서 하나를 선택하여 시스템에 반영될 것입니다.

**안티프래글(Antifragile)**
Antifragile은 단순히 장애나 변화에 대해 회복(resilient)하는 것을 넘어서, 스트레스와 변화를 통해서 오히려 시스템이 개선되고 발전하는 아키텍처를 말합니다.

안티프래글의 특징
- 자동 확장(Auto Scaling)
	- Minimum Size: 최소 갯수 설정
	- Desired Capacity : 원하는 갯수 설정
	- Maximum Size: 최대 갯수 설정
	- Scale out as needed : 필요한 경우에 확장 및 축소 가능한 갯수 설정
- 마이크로서비스(Microservices)
	- Cloud Native 핵심
	- 마이크로서비스는 전체 서비스를 구축한 후에  개별적인 모듈들을 독립적으로 개발한다.
- 카오스 엔지니어링(Chaos engineering)
	- 분산 시스템에서 탄력성, 회복성을 능동적으로 수행하고 개선하는 방법을 말합니다.
	- 단순히 장애가 발생하는 것을 기다리는 것이 아니라 의도적으로 시스템의 문제를 유발시켜서 예상치못한 문제를 발견하고 해결해서 실제 장애가 발생해도 시스템이 안정적으로 작동할 수 있도록 합니다.
	- CPU 리소스 부하걸기, 데이터센터로부터 접속 끊어보기, 입출력장치에 에러를 일으키기, 각 서비스간에 문제점을 유발시키기, 순간적으로 강한 트래픽을 주입해보기
- 지속적 배포(CI-CD, Continuous deployments)
	- 배포를 개발자가 일일히 수작업으로 하는 것은 매우 번거로움
	- 배포 작업을 자동화해서 빠르고 정확하게 배포하도록 함

## Cloud Native Archiecture
클라우드 환경 아키텍처(Cloud Native Architecture) 특징
- 확장 가능한 아키텍처
	- 시스템은 필요에 따라서 **수평적 확장(Scale-out)** 을 통해서 유연하게 서버가 늘어나거나 줄어들 수 있습니다. 수평적 확장을 통해서 시스템 부하를 분산하고 가용성을 보장합니다.
	- 시스템 또는 서비스 애플리케이션 패키지(컨테이너 기반 패키지) 단위로 확장하거나 축소합니다.
	- 클라우드 환경 아키텍처를 이용해서 **모니터링**을 수행할 수 있습니다.
- 탄력적 아키텍처
	- "서비스 생성 - 통합 - 배포" 단계를 거쳐서 **CI-CD를 통한 비즈니스 환경 변환에 대응 시간을 단축**합니다. 자동화된 CI-CD를 구축함으로써 개발자는 비즈니스 로직을 구현하는데 더욱 시간을 들이고, 배포하는데 시간을 절약할 수 있습니다.
	- 탄력적인 아키텍처는 **서비스가 분할된 구조**를 가지고 있습니다.
	- 무상태 통신 프로토콜 지원
	- 서비스의 추가와 삭제를 자동으로 감지
	- 변경된 서비스의 요청에 따라 사용자의 요청을 처리 (동적 처리)
- 장애 격리(Fault isolation)
	- 클라우드 환경 기반의 아키텍처는 장애나 복구에 능력이 좋음
	- 특정 서비스에 오류가 발생해도 다른 서비스에 영향을 주지 않음


## Cloud Native Application
**클라우드 환경 애플리케이션(Cloud Native Application) 특징**
- 마이크로서비스(Mircoservices)
- CI-CD 환경으로 통합 및 배포
- 서비스 문제 발생시 배포과정을 거치는 DevOps 방식으로 수행
- 애플리케이션을 컨테이너 기반으로 실행

**마이크로서비스(Microservice)는 무엇인가?**
- 마이크로서비스 아키텍처는 대규모 애플리케이션을 **모듈화된 구성 요소나 서비스들의 집합**으로 구축하는 **애플리케이션 개발 방식**입니다.
- 마이크로서비스는 서버를 용도별로 작게 쪼개서 독립적으로 배포 및 실행하는 방식입니다.

**컨테이너화(Containerization)**
- 컨테이너화는 배포를 위해서 가상 패키지와 격리화된 애플리케이션이 될수 있는 소프트웨어의 타입입니다.
- 컨테이너화를 통해서 어떠한 플랫폼 환경에서든 동일한 환경처럼 배포 및 실행할 수 있도록합니다.

**지속적인 전달(Continuous Delivery)**
- Continuous Delivery는 개발팀이 짧지만 지속적인 주기로 코드를 생성하고 테스트하는 소프트웨어 방식 중 하나입니다.
- CI-CD 환경 구축하기

**데브옵스(DevOps)**
- 데브옵스는 서비스를 구현 및 배포하면서 장애를 모니터링하고 해결하는 개발 방식입니다.

### Cloud Native Application - CI/CD
**지속적인 통합(CI, Continuous Integration)**
- 여러 개발자들이 코드 개발을 하면 코드를 빌드 성공하여 하나의 결과물로 합치는 과정입니다.
- 하나의 결과물로 합치기 위해서 통합 서버, 소스 관리, 빌드 도구, 테스트 도구를 사용합니다.
- 대표적으로 Jenkins, Team CI, Travis CI 툴이 있습니다.

**지속적 배포(CD, Continuous Deployment)**
- CI 과정을 통하여 통합된 결과물을 클라우드와 같은 환경에 배포하는 과정입니다.
- Github와 같은 저장소에 코드를 커밋 후 푸시하게 되면 자동적으로 CI 과정을 거쳐서 빌드되고, 결과물을 실행 환경에 배포하여 서버가 자동적으로 실행하도록 합니다.

**카나리 배포와 블루그린 배포**
- 배포할때 전략으로 카나리 배포 전략 또는 블루그린 배포 전략을 선택하여 할 수 있습니다.
- 카나리 배포 전략(Canary Deployment)
	- 배포된 서버를 한번에 다운시킨 다음 새로운 버전으로 실행하는 것이 아닌 실행중인 서버들을 점진적으로 업데이트하여 배포하는 방식입니다.
- 블루그린 배포(Blue/Green Deployment)
	- 무중단 배포 기법 중 하나
	- 블루(구버전), 그린(신버전)을 구분한 상태에서 운영중인 구버전과 동일하게 신버전의 인스턴스를 구성한 후 로드밸런서를 통해 모든 트래픽을 한번에 신버전 쪽으로 전환하는 방식입니다.

### Cloud Native Application - DevOps
**DevOps란 무엇인가?**
- 개발(Development)과 QA와 운용(Operations)를 합친것과 같이 코드를 개발하고 구현한 소프트웨어를 배포한 다음에 QA를 통하여 에러를 발견하고 해결하는 개발 방식을 의미합니다.
- 고객의 요구사항 변경시 바로바로 반영할 수 있도록 합니다.
- 자주 테스트하고 자주 피드백하여 결과물에 반영할 수 있도록 합니다.
- Cloud Native Application는 DevOps 환경에 맞추어 서비스 구조를 작은 단위로 분할하여 더 통합하고, 더 테스트하고, 자주 배포할 수 있는 구조를 갖도록 합니다.

### Cloud Native Application - Container 가상화
Container 가상화를 이용하여 애플리케이션을 배포하면 적은 비용으로 서버를 구축할 수 있습니다.

**전통적인 배포(Traditional Deployment) 구조**
- 하드웨어 위에 운영체제가 존재하고 운영체제 위에서 여러개의 애플리케이션을 배포하는 구조

**서버 가상화(Virtualized Deployment) 구조**
- 하드웨어 위에 운영체제가 존재하고 운영체제 위에서 가상화 기술을 적용합니다.
- 여러개의 가상 머신이 실행되고 가상 머신에 있는 운영체제(가상 OS) 위에서 애플리케이션을 실행하는 방식입니다.
- 가상 머신 위에서 독립적으로 실행될 수 있지만, 호스트 운영체제에 많은 부하를 주는 기술입니다.

**컨테이너 기반 배포(Container Deployment) 구조**
- 운영체제 위헤서 Docker와 같은 컨테이너 런타임 서비스를 준비하고, 컨테이너 단위로 애플리케이션을 실행하여 독립적으로 실행하도록 합니다.
- 가상화 기술과 차이점은 운영체제의 리소스를 공유할 수 있는 부분은 공유하고 컨테이너가 가져야 하는 부분은 독립적으로 가질수 있도록 합니다. 이로 인해서 작은 사이즈로 실행이 가능함

## 12 Factors
Cloud Native Application 구현시 고려해야할 12가지 요소를 확인합니다.

**코드 베이스(Base Code)**
- 애플리케이션 구현시 하나의 코드 베이스를 사용하는 것을 권장합니다.
- 하나의 코드 베이스를 기반으로 여러개의 브랜치가 생겨나고 다시 하나의 코드가 합쳐지는 과정이 수행됩니다.

**의존성 격리(Dependency Isolation)**
- 외부 라이브러리나 패키지는 명시적으로 선언하고 환경에 독립적으로 관리되어야 함을 의미합니다.

**설정(Configurations)**
- 설정 정보들은 환경 변수로 분리하고 의도와 구성을 철저히 분리해서 사용해야 합니다.

**연결 가능한 뒷단 서비스(Linkable Backing Services)**
- 데이터베이스, 메시지 큐, 레디스와 같이 외부 서비스를 내부 구성 요소 처럼 취급하지 않고 독립된 리소스로 연결해서 사용해야 합니다.

**생성 단계(Build, Release, Run)**
- 애플리케이션을 빌드하고 구성 적용을 하고 그 다음에 실행 단계를 명확히 분리하세요.

**상태 없는 진행(Stateless Progresses)**
- 애플리케이션 자체가 상태를 가지고 있지 않은 프로세스가 되어야 합니다.
- 공유되는 상태는 외부 저장소(데이터베이스, 레디스 등)에 보관되어야 합니다.

**포트 바인딩(Port Binding)**
- 애플리케이션들은 서버들 스스로 서로 다른 포트를 포함하고 있어야 합니다.

**동시성(Concurrency)**
- 프로세스들을 여러개 실행해서 수평 확장(Scale-Out) 하도록 해야 합니다.

**일회용(Disposability)**
- 애플리케이션인 프로세스가 빠르게 실행되고, 빠르게 종료되어야 한다는 것을 의미합니다.
- 예를 들어 무중반 재배포, 장애 복구가 구축되어야 한다는 것을 의미합니다.

**개발 및 프로덕션 일관성(Development & Production Parity)**
- 개발, 테스트, 운영 환경의 차이를 최소화하여 코드가 어디서 실행되든 동일하게 동작하도록 만드세요.

**로그(Logs)**
- 로그를 웹 애플리케이션 내부에서 관리하지 않고, 로그 수집기, 분석기 같은 것을 통하여 로그를 처리할 수 있어야 함을 의미합니다.

**이벤트적인 프로세스를 위한 관리 작업(admin processes for eventual proceeses)**
- 데이터마이그레이션이나 초기화와 같은 일회성 관리 작업들은 앱 코드와 같은 방식으로 처리해주어야 합니다.


### 12 Factors 강조
12 Factors에서 강조하고 있는 것은 다음과 같습니다.
- 구성(Configuration)과 코드(Code)를 분리하라
- 외부 의존성은 격리하고 선언하라
- 상태 없는 프로세스로 구성하고, 빠르게 시작하고 종료할 수 있도록 하라
- 환경 간에 차이를 최소화하고, 일관된 배포 및 실행 흐름을 갖추어라
- 로그나 관리 작업은 외부 시스템에서 제어하라

### 12 Factors + 3
12가지 요소에 더해서 요즘에는 3가지 요소를 더 이야기합니다.

**API 우선(Api First)**
- 모든 기능을 명확한 API로 먼저 설계되어야 한다는 원칙

**원격 관측성/계측(Telemetry)**
- 클라우드/분산 환경에서는 시스템 내부를 직접 들여다 보기 어렵기 때문에 **모니터링/로그/트레이스/헬스 체크**와 같은 계측을 처음부터 설계해야 한다는 원칙입니다.

**인증 및 인가(Authentication and Authorization)**
- 보안은 후순위가 아니라 설계 초기부터 고려해야 한다는 원칙입니다.

위 3가지 요소외에도 다음과 같은 강조 요소들도 존재합니다.
**관측 가능성(Observability)**
- 시스템 내부 상태를 외부 출력(로그, 메트릭, 트레이스 등)으로부터 유추할 수 있는 능력을 말한다.

**컨테이너화(Containerization)**
- 애플리케이션과 그 의존성을 하나의 경량화된 컨테이너 이미지로 묶는 기술

**자동화(Automation)**
- 반복되는 작업을 사람이 하지 않고, 시스템이 자동적으로 하도록 구성하는 것을 의미함
- 대표적으로 CI-CD 작업이 존재합니다.


## Monolithic vs. Microservice
### 모놀리식과 마이크로서비스 방식 비교
**모놀리식 방식은 무엇인가?**
애플리케이션 개발시 필요한 모든 요소를 모두 하나의 애플리케이션에 전부 포함시켜서 개발하는 방식입니다.
예를 들어 데이터베이스 로직, 비즈니스 로직, 프론트 엔드 기술까지 하나의 애플리케이션에서 수행됩니다. 모놀리식 아키텍처를 비교하면 하나의 커다란 건물에 비유합니다.

**마이크로서비스 방식은 무엇인가?**
마이크로서비스 방식은 각각의 서비스 내용을 분리해서 개발하고 운용하는 방식입니다. 모놀리식 방식을 사용하면 각 서비스의 유지보수나 변경 사항을 적용하는데 유리합니다. 해당 방식을 사용해서 각각의 서비스들이 상호작용하여 로직을 처리합니다.

### 모놀리식 아키텍처(Monolithic Architecture)
**모놀리식 아키텍처 동작 과정**
모놀리식 방식에서는 모든 비즈니스 로직이 하나의 애플리케이션에 패키지 형태로 서비스됩니다. 애플리케이션에서 사용되는 데이터 또한 한곳에 모여서 참조되어 서비스되는 형태입니다.

**모놀리식 아키텍처 예시**
다음 그림의 E-Commerce 시스템을 보면 하나의 애플리케이션에 Shop UI, Catalog Service, SC Service, Discount Service 등의 비즈니스 로직과 UI 처리 로직이 하나의 애플리케이션에 들어있습니다. 그리고 데이터는 RDBMS에 저장되어 있습니다.
![](../imgs/Pasted%20image%2020251007111246.png)

### 마이크로서비스 아키텍처
**마이크로서비스는 무엇인가?**
애플리케이션들이 작은 서비스라는 단위로 독립적으로 분할하여 개발 및 배포되어 있는 형태 

**마이크로서비스 아키텍처의 스타일**
마이크로서비스 아키텍처 스타일은 작은 서비스들이 모여서 하나의 애플리케이션을 개발하는 방식입니다. 여기서 작은 서비스들은 자기만의 프로세스로써 작동하고, 경량 방식으로 HTTP API와 같은 방식으로 서로 상호작용합니다.

마이크로서 서비스들은 비즈니스 기능을 중심으로 구축되며, 완전히 자동화된 배포 메커니즘을 통해 독립적으로 개발 및 배포할 수 있습니다.

**마이크로서비스 아키텍처 예시**
예를 들어서 어떤 회사에서 엔터프라이즈 애플리케이션을 개발한다고 가정할때 먼저 고객의 의뢰를 받은 다음에 프로젝트가 진행할 수 있게 검토 및 승인을 할 것입니다. 다음으로 개발 조직을 이루기 위해서 팀 조직(Team Building)을 할 것입니다. 
그리고 요구사항을 정의할 것입니다. 요구사항에서 도메인의 정의라든가 분석을 진행할 것입니다. 시스템 설계 과정으로 진행됩니다. 그리고 설계가 완료되서 **개발을 시작할 시점에 어떠한 프로그래밍 언어를 사용할 것인지, 어떤 데이터베이스를 사용할 것인지, 프로그래밍 네이밍 컨벤션, 인터페이스 등을 결정하고 진행할 것**입니다. 
마이크로서비스에서는 이러한 프로그래밍 개발 언어와 데이터베이스 언어를 전체 애플리케이션에서 통일하는 것이 아니라 각각의 서비스별로 특성에 맞게 최적화된 언어와 데이터베이스를 선택할 것입니다. 
예를 들어 서버 사이드 개발을 하기 위해서는 자바, 하드웨어 제어를 하기 위해서는 C, C++ 언어가 적합할 것입니다. 데이터분석을 위해서 머신러닝, AI를 사용하기 위해서는 파이썬이 있습니다. 서버 사이드에서 자바 스크립트, 비동기 서비스를 위해서 NodeJS 언어가 최적의 성능을 낼것입니다.

### 모놀리식 vs 프론트엔드 & 백엔드 vs 마이크로서비스 아키텍처
![](../imgs/Pasted%20image%2020251007125317.png)

모놀리식 방식과 마이크로서비스 방식의 중간 형태로 프론트엔드 & 백엔드 형식이 있습니다. 제일 왼쪽은 하나의 애플리케이션에 모든 로직이 포함된 방식이 모놀리식 방식입니다.

사용자에게 화면을 보여주고 사용자에게 데이터를 보여주기 위해서 프론트와 백엔드를 구분하는 방식도 있습니다. 대표적으로 모바일 애플리케이션에서 이러한 구조를 많이 사용합니다. 프론트와 백엔드가 통신하기 위해서 일반적으로 HTTP나 HTTP 위의 프로토콜을 사용합니다. 마이크로서비스 처럼 완전히 분리된 것은 아니지만 화면단과 데이터 처리단을 분리해서 처리합니다.

마지막은 마이크로서비스 아키텍처 부분입니다. 프론트와 백엔드를 분리하였으며, 백엔드 부분을 각각의 의미있는 서비스 단위로 분리하였음을 볼 수 있습니다. 이러한 백엔드단에 있는 각각의 서비스들은 독립적으로 개발 및 배포됩니다. 중간에 있는 Aggregation Layer(예를 들어 BFF, GraphQL)은 분리된 백엔드 서비스들의 데이터들을 하나로 통합하거나 프론트에 맞는 최적화되어 있는 백엔드를 별도로 구성해서 서비스를 한다던가 이렇게 마이크로서비스 아키텍처에 필요한 다양한 패턴들에서 사용되는 용어입니다.


## Mircroservice Architecture의 이해
2002년 아마존 창립자 제프 베이존스가 직원들에게 이메일을 보낸 내용입니다.

모든 팀은 앞으로 자신들의 데이터와 기능을 서비스 인터페이스를 통해서만 외부로 공개(노출)하게 될 것입니다.
```
1. All teams, will henceforth expose their data and functionally through service interfaces.
```
팀들은 인터페이스들을 통해서 서로 각자 통신해야 합니다.
```
2. Teams must communicate with each other through these interfaces.
```

다른 형태의 프로세스 간 통신은 일절 허용되지 않습니다. 즉, 직접적인 링크 연결, 다른 팀의 데이터 저장소를 읽는 행위, 공유 메모리 모델 사용, 백도어 접근 등은 모두 금지됩니다. 오직 네트워크를 통한 서비스 인터페이스 호출만이 허용된 유일한 통신 방식입니다.
```
3. There will be no other form of interprocess communication allowed no direct linking, no direct reads of another team's data store, no shared-memory model, no back-doors whatsoever. The only communication allowed is via service interface calls over the network.
```

HTTP, Corba, Pubsub, 커스텀 프로토콜을 사용하는 것은 문제가 되지 않습니다.
```
4. It doesn't matter what technology they use HTTP, Corba, Pubsub, custom protocols - doesn't matter.
```
모든 서비스 인터페이스는 예외 없이 처음부터 외부에 공개 될 수 있도록(externalizable) 설계되어야 합니다. 즉, 각 팀은 자신들의 인터페이스를 외부 개발자들에게 공개할 수 있도록 사전에 계획하고 설계되어야 합니다. 어떠한 예외도 허용되지 않습니다.
```
5. All service interfaces, without exception, must be designed from the ground up to be externalizable. That is to say, the team must plan and design to be able to expose the interface to developers in the outside world. No excetpions.
```
이 지침을 따르지 않는 사람은 누구든 해고될 수 있습니다.
```
6. Anyone who doesn't do this will be fired.
```
감사합니다. 좋은 하루 보내세요!
```
7. Thank you; have a nice day!
```

### 마이크로서비스의 특징
**모놀리식의 장단점**
- 장점
	- 코드 구현 쉬움
	- 디버깅 쉬움
	- 배포 쉬움
	- 성능
	- 상대적으로 쉬움
- 단점
	- 강결합 발생함
	- 원치 않는 변경이 발생함
	- 기술 스택에 대한 제한점을 가짐
	- 스케일 아웃이 힘듬, 모놀리식은 어떤 하나의 큰 덩어리 애플리케이션이기 때문에 확장시 모든 기능을 담은 애플리케이션이 확장됨

**마이크로서비스의 장단점**
- 장점
	- 느슨흔 결합
		- 각각의 서비스들이 독립적으로 개발되어 있기 때문에 한 서비스가 수정될때 다른 서비스에 수정 영향을 미치지 않음
	- 원치 않는 변경이 적음
		- 한 서비스의 변경이 되어도 다른 서비스에 변경 영향이 적다
	- 제한없는 기술 스택
		- 각각의 서비스들이 프로그래밍 언어와 데이터베이스 언어를 동일하게 맞추지 않고 최적화된 언어 및 저장소를 선택할 수 있음
	- 확장이 쉬움
		- 비즈니스 로직을 수행하는 서비스를 처리하는 서비스로 확장이 쉬움
- 단점
	- 네트워크 지연이 있음
		- 한 서비스에서 다른 서비스로 데이터를 가져오기 위해서 요청하고 받을때까지 네트워트 지연이 존재함
	- 데이터 일관성 문제
		- 서비스가 여러개로 분산되어 있기 때문에 분산 트랜잭션을 사용할 수 밖에 없음
		- 한 서비스의 트랜잭션이 실패하면 일관성 있게 롤백해야함
	- 객체 설계 복잡성

**아키텍처 설계 - 수직적 고려사항(Architecture Design - Vertical Considerations)**
- 어떻게 각각의 서비스를 분리할 것인가?
- 어떻게 각각의 서비스들이 서로 통신할 것인가?
- 데이터 관리는 어떻게 할것인가?
- 트랜잭션 관리는 어떻게 할것인가?
- 서비스들의 배포는 어떻게 할 것인가?
- 서비스 장애 발생시 어떻게 안정적으로 동작을 유지할 것인가?

**데이터 관리 고려사항**
- Choose Right Database(데이터베이스 선택)
	- Polyglot Persistence
		- 하나의 애플리케이션 또는 시스템이 서로 다른 데이터베이스를 조합하여 사용하고, 각 데이터 타입과 목적에 맞는 데이터베이스 기술을 선택하는 설계 방식
	- The Database-per-Service
		- 각 마이크로서비스가 자신의 데이터베이스를 독립적으로 소유하고, 다른 서비스와 데이터베이스를 공유하지 않는 설계 방식
	- The Shared Database Anti-Pattern
		- 서비스간에 공유되는 데이터베이스는 안티 패턴
- Command and Queries(명령과 조회)
	- The API Composition
		- 여러 서비스에서 흩어져 있는 데이터를 하나의 응답으로 합쳐서 클라이언트에게 제공하는 패턴을 의미합니다.
	- The CQRS Pattern
		- 명령(Command)과 조회(Query)의 책임을 분리하는 소프트웨어 설계 패턴입니다.
		- 명령은 데이터의 상태 변경 작업(추가/수정/삭제)입니다.
		- 조회는 데이터의 상태 조회(읽기)작업입니다.
	- The Event Sourcing Pattern
		- 시스템의 상태(state)를 현재 값으로 직접 저장하는 것이 아니라, 발생한 모든 이벤트(Event)의 모든 순서를 저장하고, 이 이벤트들을 재생(Replay)하여 상태를 구성하는 패턴입니다.
		- 즉, "무엇이 일어났는가"를 기록하면, 그 기록만으로 현재 상태를 재구성할 수 있다는 아이디어입니다.
- Distributed Transactions(분산 트랜잭션 관리)
	- The Saga Pattern
		- 하나의 비즈니스 트랜잭션을 여러 서비스에 걸쳐서 수행할 때, 서비스 간 데이터 일관성을 보장하면서도 분산 환경에서 트랜잭션을 관리하는 패턴
	- Transactional Outbox
		- 한 서비스에서 데이터베이스에 상태 변경을 저장할 때, 동일 트랜잭션 안에서 이벤트를 별도의 "Outbox" 테이블에 기록하고, 이후 이를 다른 서비스로 안전하게 전달하는 패턴
	- Compensating Transactions
		- 이전 트랜잭션의 효과를 되돌리기 위해 수행되는 반대 작업을 말합니다.
		- 즉, 어떤 서비스에서 수행된 작업을 취소하거나 롤백하기 위해 별도로 설계된 트랜잭션입니다.
	- CDC - Change Data Capture 
		- 데이터베이스에서 발생한 변경 사항(추가, 수정, 삭제)을 실시간 또는 근실시간으로 감지하여 다른 시스템으로 전달하는 기술
		- 즉, DB에서 무슨 일이 일어났는지 기록하고 이를 이벤트처럼 외부로 전달하는 방식입니다.

마이크로서비스 특징 정리
1. Challenges
2. Small Well Chosen Deployable Units
	- 독립적으로 배포 가능한 작은 서비스 단위
3. Bounded Context
	- 각각의 서비스들은 애플리케이션을 구성할 수 있는 전체 도메인 영역에 따라서 서비스 경계를 잘 구분해야함.
	- 서비스 경계에 따라서 여러개의 서비스가 될 수 있음
4. RESTful
	- 각각의 서비스들은 통신하기 위해서 다양한 통신 메커니즘을 사용할 수 있음
	- 예를 들어 REST API 방식으로 통신한다고 가정하면 HTTP 프로토콜을 사용하겠다는 의미.
- Configuration Management
	- 마이크로서비스들이 가지고 있는 환경 정보, 설정 정보라는 것을 코드 내에서 관리하는 것보다는 외부 시스템에서 관리하는 것을 권장하고 있음
- Cloud Enabled
	- 클라우드 네이티브 기술을 활용해서 운용하고 서비스를 제공할 수 있는 인스턴스들의 부하분산 처리
- Dynamic Scale Up And Scale Down
	- 서버 인스턴스들의 상황에 따라서 스케일 업, 스케일 아웃 처리함
- CI/CD
	- 마이크로서비스들을 통합하고 배포하기 위해서 자동화된 시스템을 사용함
- Visibility
	- 모든 마이크로서비스들이 시각화된 도구를 사용해야만 다수의 서비스들이 현재 어떤 상태이고 어떤 문제인지 확인이 가능함

### 마이크로서비스 아키텍처 도입시 고민할 사항
Q1) 어느정도의 변화가 필요할 것인가?
마이크로서비스를 도입함에 있어서 기존 개발 대비 비용과 시간이 더 투자되어야 하는 부분이 있다. 그럼에도 불구하고 도입해야 한다면 어느정도의 비용을 고려하고 받아들수 있는 것인가에 대한 문제입니다.

Q2) 독립적인 라이프 사이클
애플리케이션을 구성하고 있는 각각의 서비스들이 독립적으로 개발되고 운영될 수 있도록 서비스 경계가 잘 이루어 졌는가 하는 점입니다.

Q3) 독립적인 확장성
각각의 서비스를 운영함에 있어서 서비스의 유지 보수라든가 확장성이 유리한지 고려해야합니다.

Q4) 격리된 오류
전체 오류가 아니라 서비스가 부분적으로만 발생을 하고 더 이상 확대되지 않도록 차단 시켜 놓는 것을 말합니다. 마이크로서비스에서 부분적으로 오류가 발생할 때 해당하는 서비스에 대해서만 오류가 영향을 끼치고 그리고 다른 서비스들은 오류에 최소한의 영향을 받음으로써 해당 서비스를 우회할 수 있는 대체 서비스를 준비가 되었는가 한는 점입니다.

Q5) 외부에 있는 종속성과의 상호작용을 어떻게 단순화할 수 있는가?
외부에 대한 종속성 뿐만 아니라 시스템 또는 서비스간에 종속성을 최소화 시켜주어야 합니다. 그리고 반대로 응집력을 높일 수 있는 서비스 경계를 구분할 수 있는가 하는 점도 있습니다.

Q6) Polyglot Technology
마이크로 서비스는 독립적인 언어와 데이터베이스를 가질 수 있습니다. 우리는 이것을 Polyglot이라고 이야기 할 수 있습니다. 원래 Polyglot이라고 하는 것은 여러개의 언어를 구사할 수 있는 능력을 말합니다. 마이크로서비스에서 이야기하고 있는 서비스의 어떤 기능을 다양한 프로그래밍 언어와 다양한 데이터베이스 중에서 최적화되어 있는 것을 선택해서 개발할 수 있다고 말씀드렸습니다. 그러한 Polyglot을 마이크로서비스에서 적극적으로 수용할 수 있습니다. 우리는 이러한 프로그래밍 언어와 데이터베이스 언어를 고민해야 합니다.

### 마이크로서비스 팀 구조
- Two Pizza Team
	- 점심 한끼를 같이 먹을 수 있는 피자 두판을 나누어 먹을 수 있는 인원이 몇명이 가장 적절한가라고 보는 것입니다.
	- 예를 들어 피자 한판을 2명이서 먹는 한팀에 4명이 적절하다고 볼수 있음
- 팀들은 API 를 기준으로 소통합니다.
- 팀들은 각각의 서비스들을 독립적으로 개발, 테스트, 배포합니다.
- Consumer Driven Contract
	- 서비스를 소비하는 쪽(Consumer)이 요구하는 계약(Contract)을 정의하고, 제공하는 서비스(Provider)는 이 계약을 만족하도록 구현 및 테스트 하는 패턴

## SOA vs MSA
**SOA(Service Oriented Architecture)**
- 비즈니스 측면에서의 서비스 재사용성
- ESB(Enterpriese Service Bus)라는 서비스 채널 이용 -> 서비스 공유, 재사용
	- 각각의 서비스를 관리하기 위해서 ESB 이용함

**MSA(Microservice Achitecture)**
- 한가지 작은 서비스에 집중
- **서비스 공유하지 않고, 독립적으로 실행함**

**서비스의 상대적 크기와 관심사**
- MSA는 작은 서비스에 집중하는 반면에 SOA는 비즈니스에 집중하여 상대적인 크기가 SOA가 더 큽니다.

**서비스의 오너십(Ownership)**
- 마이크로서비스 아키텍처는 하나의 팀에서 여러개의 서비스들을 개발 및 배포하면서 개발 및 관리합니다.
- 반면에 SOA는 하나의 SOA에 업무, 미들웨어 시스템, 서비스 조합 개발과 같은 서비스가 각각 포함되어 있을때 업부/기술/개발 조직이 각각 다릅니다.

**서비스 공유의 지향점**
- SOA - 재사용을 통한 비용 절감
- MSA - 서비스간의 결합도를 낮추어 변화에 능동적으로 대응
- 서비스를 MSA에서는 서비스 공유를 최소화하기 위해서 사용하고, SOA에서는 반대로 서비스 공유를 최대화하기 위해서 사용한다.

**기술 방식**
- SOA - 공통의 서비스를 ESB에 모아서 사업 측면에서 공통 서비스 형식으로 서비스 제공
	- ESB(Enterprise Service Bus) : 기업 내 서비스간 통신을 담당하는 버스
	- WSDL(Web Service Description Lanuage): 웹 서비스 사용 설명서, 각 서비스가 어떤 기능을 제공하는지, 어떤 형식으로 요청/응답을 주고받는지를 정의한 XML 문서
	- UDDI(Universal Description, Discovery and Intergration) : 서비스 전화번호부, ESB가 연결할 수 있는 서비스 목록을 보관하는 저장 역할
- MSA - 각 독립된 서비스가 노출된 REST API를 사용함

> Service Discovery는 서비스들이 서로의 위치(IP/Port)를 동적으로 찾을수 있게 도와줍니다. 주요 기능은 동적으로 생성된 서비스 인스턴스(IP, Port) 등록 및 조회, 서비스 헬스체크 및 제거, 로드 밸런싱 지원이 있습니다. 비유로 따지면 Service Discovery는 건물 내부의 안내 데스크입니다.

## Microservice Architecture Structures 1
### MSA 특징
작은 서비스
- 서비스들이 독립적으로 수행됨
- 에릭 에반스 "도메인 주도 설계(Domain Driven Design)"
	- Bounded Context : 하나의 서비스에 담을 수 있는 기능들의 그룹, 서비스들의 경계
		- 하나의 서비스에 단일 기능이 있을 수 있고, 여러개의 기능이 모여서 하나의 서비스로 구성될 수 있음
		- 예를 들어 사용자 서비스에는 사용자와 관련된 기능들만이 존재하고, 주문 서비스에는 주문과 관련된 기능들이 모여있습니다.
	- Ubiquitous Language : 같은 업무를 하는 사람들은 같은 단어와 용어를 사용한다는 의미
		- 우리는 도메인 주도 설계를 할때 유비쿼터스 언어를 사용하여 같은 업무를 하는 사람들끼리 같은 의미의 단어와 용어를 사용해야 한다.

CRM 애플리케이션에는 고객 관리 기능, VOC 관리 기능, 계약 관리 기능이 존재하는데 이 3가지 기능 모두 "고객"이라는 용어를 사용하고 있지만, 서로 다른 의미를 가지고 있습니다. 계약 관리 기능에서 고객이라는 용어는 "가입자"를 의미할 수도 있습니다. VOC 관리 기능에서 고객은 "상담을 하는 접수자"일수 있습니다.
위와 같이 보편적으로 사용되는 "고객"이라는 용어가 서로 다르게 해석될 수 있기 때문에 서비스를 분할 가능한 형태로 나누는 것이 필요합니다. 

독립된 서비스
- MSA는 독립적으로 실행하고 다른 서비스 결합이 없는 서비스들로 구성되어 있습니다.
- 다른 서비스가 구현, 배포, 실행, 장애가 발생하여도 다른 서비스에 영향을 미치지 않음
	- 예를 들어 "고객 관리 서비스"중 고객 등록 기능에 문제가 생겨도, 이와 관계없이 예약이 가능함

응집된 서비스
- 하나의 서비스는 기능적으로 응집되어 있다
- 서비스의 역할이 한가지 일을 위해 묶여야 함 -> 단순 명확, 오류 최소화
	- 예를 들어 수강 신청 시스템이 존재함

자율적 서비스
- 서비스의 기획, 개발, 테스트, 배포 및 서비스 운영까지 담당 조직이 독립적으로 의사 결정할 수 있어야 함
	- 이것을 서비스의 오너십(Ownership)이라고 함
- 개발환경과 테스트 환경, 실행 환경이 동일하게 유지되어야지만 개발에서부터 운영까지 하나의 팀이 처리할 수 있는 형태를 이룰수 있습니다.

### Microservice 기획
Microservice 식별 전략
마이크로서비스를 식별하기 위한 전략은 4단계로 구성됩니다.
- 도메인 이해 / 요구 분석 / 조직 분석 단계
- 마이크로서비스 원칙 수립 단계
- 상관 분석 단계
- 서비스 식별 단계

마이크로 서비스를 식별하기 위해서 필요로 하는 비즈니스 도메인이 있을 것입니다. 도메인은 서비스를 만들기 위해서 애플리케이션의 주제나 특징을 의미합니다. 이는 도메인은 가장 상위의 개념입니다. 이러한 하나의 도메인을 서브 도메인들로 분리되고 업무에 대해서 분리하고, 어떠한 기술을 사용할 것인지 정의될 것입니다.

**도메인 이해 / 요구 분석 / 조직 분석 단계**
도메인 이해 / 요구 분석 / 조직 분석 단계에서 해당 서비스를 구현하기 위해서 사용자, 업무 흐름, 핵심 업무, 업무 우선순위를 정합니다.

간단한 예시를 들자면 도메인 중에서 업무 기능 중에서 업무 특성 또는 기능 분할을 하고 우선순위에 따라서 중요도, 영향도를 고려하여 Pilot, MVC로 대상을 설정합니다.
어떠한 도메인으로부터 비즈니스로써 만들수 있는 애플리케이션에 대략적인 기회가 생겼다고 하면, 특화 기능, 공통 기능, 일반 기능, 솔루션 매체 기능, 배치 기능, API 기능 설계와 같은 기능들을 각각 기능들로 분리할 수 있습니다.
또는 데이터 분할 전략이라고 해서 각각의 서비스들이 사용할 수 있는 데이터를 기존에 사용했었던 하나의 데이터베이스를 사용하는 것이 아니라 서비스별로 고유의 데이터를 사용할 수 있게끔 어떻게 데이터간의 관계를 생각하고, 그 데이터를 분류할 것인지도 고민해야 할 것입니다.

**마이크로서비스 원칙 수립 단계**
도메인을 이해하고 요구분석, 조직 분석이 끝난 다음에는 마이크로서비스를 구분하기 위해서 일종의 어떠한 원칙을 수립하는게 필요합니다. **마이크로서비스의 경계라든가 분할을 시켜주는 방법이라든가 크기를 걸정해야 합니다.**
어떠한 업무를 할것인지 결정했다면 실제 기술로써 마이크로서비스를 사용할 것이기 때문에 그러한 마이크로서비스에 필요한 기술이 어떤 것이 있는지 결정하는 부분입니다.
예를 들어서 상위 개념의 서비스를 가지고 우리가 서브 도메인 즉, 하위 개념의 서비스를 생각하면서 데이터를 분리시켜 주는 방법도 있을 것 같습니다. 이러한 것들을 업무의 중요도라든가 형태라든가 팀의 크기에 따라서 **하향식으로 접근**하는 방법입니다.
반대로 **데이터의 연관성이나 그 데이터를 어디에서 사용하는지 오너십에 따라서 상향식**으로 올라가는 서비스 분할 정책도 살펴볼 수 있습니다.
다음으로 비즈니스 영향이 덜한 서비스들부터 점진적으로 바꿔가는(분할) 방법도 많이 사용합니다. 신규 시스템을 구축해야 되는 상황에서는 상관없지만 기존의 시스템으로부터 분리하고자 할때는 **원래 있었던 서비스하고 분리돼서 또는 별도로 실행해도 무방한 서비스부터 차근차근 서비스 분할을 진행하는 방법도 서비스의 식별 전략으로 사용**되고 있습니다.

**상관 분석 단계**
마이크로서비스에 어떻게 식별할 것인지 분류할 것인지 원칙이 수립되었다면 이제 **각각의 사용자나 업무성, 데이터간 상관관계가 있는지에 따라서 서비스를 다시 한번 정리**하는 것이 필요합니다.
예를 들어 서비스와 데이터의 관계를 생각해보겠습니다. 서비스가 될 수 있는 여러가지 후보중에서 어떤 것을 데이터로 만들 것인지 고민해야 합니다. 최소한 데이터간의 논리적인 경계를 구분할 수 있는 스키마 단위로 나누는 것이 가장 기초적인 방법입니다. 
다음으로 서비스간에 종속성을 생각해야 합니다. 기능간의 사용 관계와 결합도를 분석해야 합니다. 기능 내부의 함수에서 HTTP 프로토콜이나 메시지 큐 방식을 이용해서 API를 호출하고 어떻게 각각의 서비스가 관게가 있는 것인지 정리해야 합니다.
데이터 간에도 종속성이 발생할 수 있습니다. 데이터간의 종속성을 분리하기 위해서는 마이크로서비스 단위 별로 데이터베이스를 분리하는 정책을 사용하기도 합니다. 라이센스 비용의 문제로 분해할 수 없는 경우에는 스키마 정도라도 분리해서 서비스에 대응하면 좋습니다.
스키마를 분리했을 때 트랜잭션에 대한 처리를 어떻게 할 것인지 우리가 데이터를 읽기 전용과 쓰기 전용으로 나누어서 사용할것인지, 분산 트랜잭션을 어떻게 할것인지 그러한 부분도 데이터의 종속성에 따라서 나누어질 수 있습니다. 

**마이크로서비스 간 데이터 연계**
일단 서비스가 2가지 있다고 가정할때 각각의 서비스가 독립적인 UI를 가지고 있는 상황입니다. 그리고 서비스에 필요하다면 각각의 서비스를 API로 호출해서 사용할 수 있는 상태입니다. 그런데 마이크로서비스는 독립적인 화면과 독립적인 비즈니스 로직, 데이터 저장소를 가질수 있습니다. 만약에 이 2가지의 데이터 저장소를 서로 공유해야 하는 상황이 생긴다고 하면, 이전 같으면 공유 데이터베이스를 사용했기 때문에 크게 문제가 되지 않지만 이제 마이크로서비스에서는 독립적인 데이터 저장소를 갖게 되었습니다. 
예를 들어 첫번째 서비스의 데이터 저장소에 속성1, 속성2와 같은 정보를 가진 스키마가 있다고 가정합니다. 두번째 서비스의 데이터 저장소에 속성2, 속성3과 같은 정보를 가진 스키마가 있습니다. 두 스키마는 속성2가 공통사항입니다. 공통사항이라는 것은 서로 다른 서비스의 데이터저장소의 스키마에 속성2 정보가 중복되어 저장되었다는 의미입니다. 예전 같으면 데이터 모델링을 통해서 데이터가 중복되지 않게끔 저장되는 것을 원칙으로 했을 것입니다. 그러나 마이크로서비스로 넘어오면서 스토리지가 각각 독립적으로 운영되고 저장될 수 있기 때문에 비록 서비스가 중복되어도 그 편이 마이크로서비스 아키텍처를 구성하면서 훨씬 더 유리하다고 판단되면 우리는 중복을 인정하고 최종적인 일관성에 집중해서 개발하는 것이 마이크로서비스의 특징입니다. 
그리고 만약 이러한 중복 데이터가 동시에 업데이트가 되어야 하는 상황이라면 메시지 브로커(메지지 큐 방식)를 이용해서 데이터를 공유하게 됩니다. 예를 들어 서비스1의 데이터 저장소가 업데이트되면 그 변경된 데이터를 메시지 형태로 발행(Publish)합니다. 그리고 그러한 메시지가 필요한 다양한 서비스에서 구독(Subscribe) 방식으로 대기하고 있다가 메시지가 변경되었다고 알려주게 되면 그 메시지를 가지고 가서 자신이 가지고 있는 데이터도 업데이트하는 방식을 사용하게 됩니다.
데이터가 메시지 큐 방식으로 수행되어 동기화하는데 일정 시간이 소요될 수 있습니다. 따라서 서비스 중간 중간에는 그러한 동기화가 맞지 않을 수도 있으나 최종적으로는 일관성있게 맞는다. 이것이 Eventual Consistency라고 해서 최종적인 일관성을 지향하고 있는 마이크로서비스의 전략입니다.

모든 서비스가 이렇게 최종적인 일관성을 지향하지 않을 수 있습니다. 따라서 강력한 일관성, 즉, 동시성(Concurrency)을 가져야 되는 상황이라면 데이터 저장소를 공유해서 사용하는 예전 방식을 그대로 유지하세요. 반면에 지금 말하는 것처럼 데이터가 실시간으로는 일치하지 않더라도 최종적으로 일치하면 된다는 최종적인 일관성을 추구하는 서비스가 있다면 이러한 메시지 브로커를 이용해서 처리하는 것도 가능합니다.
심지어는 강력한 일관성과 최종적인 일관성을 다 허용할 수 있는 형태로써 하이브리드 형식의 시스템을 구축하기도 합니다.

**서비스 식별 단계**
마지막 단계로써 식별된 서비스의 고유한 주소나 서비스의 독립성을 가질수 있도록 준비하는 단계입니다.
서비스를 식별함에 있어서 고려해야 하는 상황 중에서 **조직**을 한번 생각해야 합니다. 예전에 우리는 **코네이 법칙**이라는 용어를 종종 사용했습니다.
코네이 법칙은 조직의 구조가 서비스의 구조로 대변한다는 정의입니다. 예를 들어서 어떤 조직에서 아키텍처, 즉 서비스를 구성하고자 할때 그 조직이 가지고 있는 규모만큼 서비스를 설계합니다.

**마이크로서비스 고려사항 : 조직의 구성**
조직의 규모가 커지면 커질수록 서비스에 대한 아키텍처를 복잡하게 설계하려는 경향이 있다는 뜻입니다. 마이크로서비스는 작은 단위의 서비스를 만드는 것이기 때문에 그러한 서비스 즉, 그러한 조직을 작게 가겨가는 것이 필요하다는 뜻입니다.
우리가 서비스를 개발하기에 앞서서 조직을 재구성하거나 가지고 있는 조직에 어떠한 팀과 어떠한 팀원이 있는지 그것부터 파악하는게 필요합니다.
마이크로서비스를 하더라도 UI를 가지고 있을 것이고, 비즈니스 로직, 개발, 테스트의 모든 과정에 대해서는 동일하게 진행할 것이기 때문에  팀 구성에 디자이너, 기획자, 아키택트, 개발자, 테스터와 같이 온전한 팀으로 유지하는 것도 필요합니다.

**마이크로서비스 고려사항 : 애자일과 데브옵스**
마이크로서비스의 궁극적인 목표는 민첩한 서비스가 가능하게 하는 것입니다. 기획에서부터 배포까지 빠르게 개발을 해서 빠르게 배포하는 방식을 추구합니다. 우리는 애자일이라는 용어로 이러한 프로세스를 강조하고 있습니다. 즉, 애자일 프로세스는 반복적이고 점진적인 개발 방법과 소통을 원할이 하는 개발 방식입니다.
애자일 프로세스에서 다루고 있는 기획, 개발, 빌드, 테스트, 배포, 운영 그리고 이러한 모든것에 이르기까지 자동적으로 이루어 낼 수 있도록 데브옵스(DevOps)를 지향하고 있습니다.
![](../imgs/Pasted%20image%2020251012151509.png)

애자일 프로세스를 진행하기 위해서 우선은 우리가 해야 할 업무를 **백로그**로 쭉 등록합니다. 어떤 업무가 필요한 건지 전체 서비스에서 등록한 다음에 그 업무들을 **이번 기간에 할 수 있는 단위**로 쪼개서 진행을 하게 됩니다.
애자일 프로세스에서는 "이번 기간에 할 수 있는 단위"를 **스프린트(Sprint)** 라고 합니다. 스트린트 기간은 1주, 2주, 4주와 같이 설정한 다음에 그 스프린트안에서 할 수 있는 업무를 **기획에서부터 테스트**까지 하나의 사이클로 계속 반복하면서 진행합니다. 이러한 애자일 설명을 통하여 애자일과 데브옵스는 뗄 수 없는 관계라는 것을 알 수 있습니다.
이전 워터폴 방식이라고 해서 처음 결정된 방식을 다시 거꾸로 올라가서 수정하는 것이 어려웠던 그러한 시기가 아니라 우리가 필요한 내용에 대해서 고민하고 개발하고 배포하고 모니터링합니다. 이러한 애자일 프로세스의 사이클을 지속적으로 가져가면서 궁극적으로 소비자가 원하는 완벽한 서비스를 만드는데 목적을 두고 있습니다.

### 서비스 분해(Service Decomposition)
서비스 분해는 다음과 같은 과정으로 진행됩니다.
1. 비즈니스 도메인 분석(Business Domain Analysis)
2. 서비스 경계 설정(Bounded Contexts)
3. 분해 전략(Decompose Strategies)
4. 마이크로서비스 경계 식별(Identity Microservice Boundaries)

서비스 경계 설정(Bounded Contexts)에서 말하는 Context는 해당하는 비즈니스에 맞는 이해를 같이 할 수 있는 공간까지를 Context라고 볼수 있습니다. 더 간단하게 말하면 **서비스가 집중할 수 있는 기능**과 **비즈니스를 함께 이해할 수 있는 다양한 형태의 기능들의 묶음**을 Bounded Context라고 볼수 있습니다.

**서비스 분해 예시**
예를 들어 우리가 **쇼핑몰**이라는 서비스가 있다고 가정합니다. 전체 애플리케이션 아키텍처로 봤을때 하나의 공통된 목표는 쇼핑몰일 것입니다.
그런데 그 서비스를 구현하고 있는 다양한 세부적인 서브 도메인을 보니 **상품(Product), 장바구니(Cart), 사용자(User), 주문(Order), 결제(Payment)** 에 대한 서비스가 존재합니다. 
각각의 서비스는 다른 서비스에 영역을 침범하지 않으면서 서비스가 가지고 있어야할 기능에 충실하고 있습니다.
서비스들은 각가이 독립적인 스토리지(예: 데이터베이스)를 가지고 있으면서 하나의 변경사항이 다른쪽에 영향을 미치지 않도록 합니다.
서비스들의 경계(Bounded)가 분명하고 독립적인 스토리지를 가지고 있기 때문에 다른 서비스에 영향을 받거나 주지 않으면서 개발 및 배포할 수 있는 것이 마이크로서비스의 특징입니다.

서비스 분해의 목적
- 마이크로서비스들간에 독립적인 개발, 확장 및 배포를 위함

**서비스 분해는 무엇인가?**
마이크로서비스에서 어떤 부분이 독립적으로 확장과 배포가 될지를 명확하게 설계하는 과정이 서비스 분해입니다.

서비스 분해를 설계하기 위해서는 우선은 요구사항을 분석하고 요구사항에 따라서 서비스 분해해야 합니다. 추후에는 확장성을 고려해서 서비스를 분해하는 것이 필요합니다.
온라인 쇼핑몰의 경우에는 공개 웹 사이트와 관리자 웹 사이트 영역을 따로 구분을 해서 서비스에 대한 분해 전략을 별도로 진행하는 것이 필요합니다.
그래서 어떠한 비즈니스 도메인이 존재하는 경우에 그러한 도메인을 처음부터 끝까지 다 한번에 한다기보다는 우리가 생각하고 있던 서비스의 업무라든지 기능에 따라서 나래비를 세운 다음에 그러한 서비스가 어떠한 서비스와 같이 관련성이 있어서 모을수 있는지 고민해야 합니다. 그렇게 모아졌던 서비스가 다른 서비스하고 독립적으로 구분이 되서 개발될 수 있겠다고 한다면 서비스 분해를 잘하고 있는 것입니다.

### 다형적인 영속성(Polyglot Persistence)
Polyglot이라는 것은 여러 언어를 구사할 수 있는 능력을 의미합니다. 즉, Polyglot Program은 패러다임을 달리해서 여러개의 언어를 자유롭게 구사 할 수 있는 기능입니다.
여러개의 프로그래밍 언어를 배운다는 것은 다양한 특징과 패러다임을 접하고 많은 아이디어를 접할 수 있다는 것을 뜻합니다. 예를 들어 Document 스토리지, key-value 스토리지, RDBMS, Graph, Search와 같이 다양한 스토리지가 존재합니다. 이러한 스토리지들이 어떠한 기능에 사용되는지에 따라서 선택할 수 있는 범위가 달라집니다.
검색이라는 기능에 있어서는 검색형 데이터베이스가 효과적일 것입니다. 어떤 업무를 수행하거나 결제 수행하거나 비즈니스 로직을 수행함에 있어서 SQL과 같은 구조화된 데이터를 사용해야 한다면 RDBMS 사용을 권장합니다.
세션을 저장해야 한다는 것은 이러한 세션이 일시적으로 발생하고 일시적으로 저장된 다음에 다시 새롭게 만들어지는게 필요하다고 가정햇을때 RDBMS보다는 NoSQL로 구분되는 Document, key-value 저장소를 사용할 수 있을 것입니다. 
이렇게 **하나의 애플리케이션을 구성함에 있어서 독립적인 하나의 데이터베이스만을 선택하는 것이 아니라 각각의 기능별로 다양한 스토리지를 선택할 수 있습니다.** 이것이 Polyglot Persistence라고 합니다.

## Microservice Architecture Structures 2
### MSA 표준 구성 요소
![](../imgs/Pasted%20image%2020251021155931.png)

이 그림은 2018년도에 나온 그림입니다. 많은 아키텍처가 위 그림를 기반으로 구현되어 있습니다.
먼저 아키텍처에 관련된 기술적인 표준은 없을 수 있습니다. 그러나 리눅스 운영체제의 산하기관인 Cloud Native Computing Foundation(CNCF)에서 각각의 시스템과 그리고 그러한 시스템을 구성하는 서비스별로 CNCF의 솔루션이나 널리 사용되고 있는 기술에 대해서 소개를 하고 있습니다. 이러한 기술을 이용해서 마이크로서비스 아키텍처를 구성할때 어떠한 항목들을 어떠한 제품들을 쓸수 있는지 그러한 구성요소라고 이해하시면 좋을것 같습니다.

먼저 앞에 있는 그림을 볼때 우리는 Inner Architecture, Outer Architecture, Outer Achitecture에 대한 호환 제품(Capability)같이 3가지로 구분해서 보시면 좋습니다.

그림의 왼쪽을 보면 "모바일 애플리케이션", "웹 브라우저", "다른 마이크로 서비스", MSA를 사용할 수 있는 플랫폼 오퍼레이터, 서비스 개발자 등이 있습니다. 이러한 사용자 또는 클라이언트들이 아키텍처를 사용하고 있습니다.

Inner Architecture라는 것은 비즈니스 도메인을 가지고 있는 것이라고 구분하시면 좋겠습니다. 여기서 말하는 비즈니스 도메인이라는 것은 **어떠한 애플리케이션을 만들기에 있어서 필요한 기능을 가지고 있는 것**을 비즈니스 도메인이라고 보시면 좋겠습니다. 예를 들어 비즈니스 도메인으로는 쇼핑몰, 리테일, 공공, 스마트 팩토리 등과 같이 우리가 필요로 하는 각각의 서비스의 분야가 존재합니다. 그러한 분야에 맞는 비즈니스 로직을 가지고 있는 것을 Inner Architecture라고 합니다.

위 그림에서 Inner Architecture는 진한 남색으로 되어 있습니다. A, B 인스턴스로 구성되어 있습니다. 그리고 Inner Architecture가 외부에 공개되고자 할때 API를 열어놔야 하기 때문에 API 역시 Inner Architecture에 속합니다. 

다시 말해서 어떠한 기능이 정해졌으며 그러한 기능을 만들기 위해서 비즈니스 로직을 만듭니다. 그러한 비즈니스 로직을 외부에 공개를 하거나 다른 서비스가 사용되게 하기 위해서는 우리는 API라는 것을 설계하게 됩니다.
그리고 비즈니스 도메인 비즈니스 기능을 가지고 있는 어떤 서비스들을 인스턴스 환경에서 운영하게 될 것입니다. 그러한 인스턴스가 한개가 아니라 여러개로 확장이 되서 사용자의 요청이 많아지면 많아질수록 인스턴스들이 N개까지 확장을 해서 운영을 하게 될 것입니다.
따라서 A하고 B라고 되어 있는 부분은 비즈니스 영역에 관련되어 있는 기능을 가지고 있다고 보면 됩니다. 

두번째는 Outer Architecture 입니다. 외부 아키텍처로는 External Gateway, Service Mesh, Runtime Platform, CI/CD Automation, Backing Service, Telemetry와 같이 크게 6가지 카테고리로 구분하고 있습니다. Outer Architecture 카테고리 안에 속해져 있는 제품들이 어떤것이 있는지를 하늘색으로 표시하고 있습니다. 

일단 게이트웨이(Gateway)에서 하는 역할과 제품들이 어떤게 있는가 살펴봅니다. **게이트웨이라는 것은 사용자들의 단일 진입점을 만들어주는 것이 게이트웨이의 역할입니다.** 게이트웨이에서 인증 처리, 로깅 정보, 필터링와 같은 것들을 제어함으로써 들어오는 것과 나가는 것들을 다 통제하는 역할을 수행합니다.

Runtime Platform이라는 것은 운영 환경, 실행 환경을 의미합니다. 조금 전에 말씀드렸던 비즈니스 로직을 실행해야 하는데 어떠한 환경에서 실행할 것인지를 의미합니다. 예전 같으면 실행 방법 자체가 서버를 그대로 만들어서 사용하거나 아니면 가상 환경, 즉, 가상 머신에서 실행했을텐데 이제는 그러한 환경을 더 작은 단위로 가져가면서 컨테이너 관리를 하고 컨테이너 가상화를 쓴다고 말씀드렸습니다.
그리고 이러한 A 비즈니스 서비스와 B 비즈니스 서비스와 같은 그런 것들이 N개까지 만들어져 있어야 하기 때문에 이러한 모든것들을 전부 다 가상 머신으로 만든다고 하면 리소스 낭비가 심해질 것입니다.
그래서 빠르게 실행, 종료, 배포하고 확장할 수 있는 구조를 가져가기 위해서 **컨테이너 런타임**을 사용하는것이 일반적입니다.
다음으로 이러한 컨테이너가 수십, 수백개를 가지고 있는 상태에서 마이크로서비스 아키텍처를 구성합니다. 서비스들이 지속적으로 통합하고 지속적으로 배포되는 환경을 구축하기 위해서는 CI/CD 자동화 처리(CI/CD Automation)를 해주어야 합니다.
CI/CD Automation 영역에는 Build Automation, Image Repository, Deployment Automation, Platform Automation이 구성되어 있습니다. 
제일 먼저 코드가 만들어지면 컴파일과 빌드해야 합니다. 빌드 과정에서 우리가 알고 있는 패키징 형태가 만들어집니다. 그렇게 만들어진 패키징되어 있는 형태가 독립적인 WAS 형태에서 실행되는 것이 아니라 도커 형태로 실행됩니다. 도커 컨테이너 단위로 실행되기 위해서는 컨테이너가 이미지 형태로 만들어져 있어야 합니다. 마이크로서비스에서 사용하는 이미지라는 용어는 OS 이미지라고 생각하시면 됩니다.
그리고 그렇게 만들어진 컨테이너 이미지를 Image Repository에 저장합니다. 해당 Image Repository는 도커 허브가 될수 있고 개인 서버가 될수도 있습니다.
Image Repository에 저장되어 있는 이미지를 가지고 와서 배포 작업을 수행합니다. 그 배포 작업을 CI/CD에서 말하는 CD(Continuous Deployment) 작업에서 자동적으로 처리할 것입니다.

그리고 이러한 처리가 CI/CD의 모든 작업의 끝이라고 보실수도 있지만, 제일 마지막 단계에서는 애플리케이션만 배포하는 것이 아니라 **플랫폼 자체도 자동화해서 관리할 수 있어야 합니다.** 플랫폼(Platform)이라는 것은 우리가 가지고 있는 운영체제를 준비한 다음에 미들웨어를 준비를 하고 필요하다고 하면 애플리케이션 서버를 준비를 하고 방금 개발했던 애플리케이션 자체를 배포해서 사용할 수 있는 모든 환경을 플랫폼이라고 보실수 있을 것 같은데, 이런 것들을 다 준비하기 위해서 수작업으로 하는 것이 아니라 **자동으로 서버를 만들어주고 자동으로 미들웨어 준비를 하고, 자동으로 애플리케이션을 배치하는 이런 모든 것들에 대해서 우리는 플랫폼 오토메이션(Platform Automation)** 을 만들수가 있습니다. 이러한 것들을 최근에는 Infrastructure as code라고 해서 모든 과정에 대해서 스크립트로 만들어 놓은 다음에 스크립트를 실행시켜서 빠르고 쉽게 Infrastructure Platform을 만들수 있도록 지원할 수 있습니다.
이러한 IaC(Infrastructure as Code, 코드형 인프라) 도구로써 대표적으로 Ansible, Terraform 같은 제품을 많이 사용하고 있습니다.

**Backing Service**라는 것은 애플리케이션들이 실행함에 있어서 독립적으로 저장할 수 있는 어떤 저장소나 메시지 서비스 같은 것들을 의미합니다. 즉, 서비스가 기동하기 위해서 부가적으로 지원되어야 하는 다양한 서비스를 백엔드 서비스를 이야기하고 있습니다.

**텔레메트리(Telemetry)**라는 것은 서비스가 한두개가 아니라 수십, 수백개가 있다 보니까 심지어는 그러한 서비스를 관리하기 위한 다양한 오픈 아키텍처 제품이 있다 보니까 지표가 필요할 것이고 모니터링이 필요할 것이고 문제가 생긴 점에 대해서 어떻게 빠르게 조치할 것인지 판단을 내려줘야 됩니다. 따라서 마이크로서비스의 진단, 모니터링 이런 것들을 담당할 수 있는 영역도 새롭게 필요하게 됐습니다.

**서비스 매시(Service Mesh)** 라는 마이크로서비스 아키텍처를 구성할 수 있는 통신 방법과 네트워크에 관련된 애기라고 생각하시면 좋겠습니다. 일단 수십, 수백개의 서비스가 생성되다 보니까 그러한 **서비스를 관리하기 위한 정보가 필요**합니다. 그래서 언제 서비스가 만들어졌고 그러한 서비스가 어디에 위치하고 있으며 해당하는 서비스를 호출하기 위해서 어떠한 방법을 선택해야 되는지 등등 이런것들을 관리하는 것을 **서비스 디스커버리(Service Discovery)** 라고 보시면 좋을것 같습니다.

일단 서비스를 등록하기 위해서 서비스 레지스트리(Service Registry)가 사용이 될 것이고, 서비스 레지스트리에 등록된 서비스들을 검색하고 찾기 위해서 서비스 디스커버리 서비스가 필요하게 됩니다. 그러면 앞으로 저희는 네이밍 서비스(Naming Service) 또는 서비스 레지스트리 또는 서비스 디스커버리라고 표현했을 때는 다 비슷한 의미의 서비스를 관리해주는 것이라고 보시면 좋을 것 같습니다.

각각의 마이크로서비스를 사용할때 환경 구성 정보가 필요한 경우에 외부에 있는 스토리지를 별도로 사용해 줌으로써 각각의 마이크로서비스는 환경이라든가 어떠한 설정 정보를 변경함에 있어서 다시 배포하지 않도록 도와줄 수 있도록 우리는 Configuration 서비스를 외부에 두어서 사용을 하게 될 것입니다.

보통 이러한 Configuration 서비스를 git 시스템에서 추적하면서 계속적으로 버전 관리를 해주면서 사용하는게 일반적입니다. 서비스 매시 영역의 밑에 보시면 서비스 라우터(Service Router)와 로드 밸런싱(Load Balancing) 기능이 포함되어 있습니다. 이 기능들은 일반적인 라우터 및 로드 밸런싱 기능과 동일합니다.

외부로부터 요청이 들어와서 어디로 가야될 것인지 Service Router에게 물어보게 됩니다. 서비스가 저장되어 있는 곳이 서비스 디스커버리입니다. 외부에서 요청이 들어왔을 때 어디로 가야 되는지 서비스 디스커버리에 물어보고 어디로 가라고 명령을 내려주는 것이 서비스 라우터의 역할입니다.

로드밸런서는  하나의 서비스가 하나의 사용자에게 필요로 하는 기능을 응답하는 것이 아니라 여러개의 사용자가 요청이 들어올때 부하 분산 처리가 돼서 동일한 서비스가 여러개 만들어져서 행동하고 있습니다. 로드밸런서는 사용자의 기능 요청을 어떤 서비스가 수행할 것인지 결정합니다. 이러한 로드 밸런서 기능까지 서비스 매시라는 영역 안에 포함하고 있습니다.

물론 Spring Cloud를 이용한다면 서비스 디스커버리, 라우터, 로드밸런서, 게이트웨이는 각각의 분리되어 있는 서비스 형태로 기동이 될것입니다. 더 나아가서 최근에 마이크로서비스 아키텍처를 가장 잘 지원할 수 있는 그런 환경으로서 **쿠버네티스(Kubernetes)** 와 같은 **오케스트레이션(Orchestration)** 도구를 사용하고 있습니다. 쿠버네티스에서는 서비스 매시라는 기능 자체가 쿠버네티스가 가지고 있는 오브젝트인 Ingress, Service, Istio를 통해서 지원하고 있습니다.

이번장에서 가장 중요한 그림이 위 그림입니다. 위 그림은 마이크로서비스 구성 요소에 해당합니다. Inner Architecture는 비즈니스 로직이므로 크게 기억하지 않아 됩니다. 하지만 Outer Architecture에서 각각의 영역이 무슨 역할을 하는지와 해당 역할을 수행하기 위해서 필요한 제품들이 어떤 것들이 있는지 기억해 놓고 더 좋게는 이러한 그림의 관계와 그림 정도를 어떻게 연관되어 있는지 그려보면 실제 마이크로서비스 아키텍처를 구상할때 큰 도움이 될 거라고 생각합니다.

### Service Mesh Capabilities
서비스 매시는 다음과 같은 기능을 가지고 있습니다.
- Configuration
- Routing
- Load Balancing
- Service Discovery
- Authentication/Authorization
- Resiliency
	- 필요한 데이터가 문제가 발생했을때 빠르게 회복할 수 있는 능력
- Encryption
	- 암호화/복호화 관련된 작업

위와 같은 서비스 매시에서 지원하는 기능들이 마이크로서비스인 나노 서비스에서 만들어졌을때 서비스별로 필요한 사항을 전부 제어할 수 있는 역할을 하는 것이 Outer Architecture의 서비스 매시의 역할입니다.

- 자가 치유 복구 서비스

#### RESTful Web Service
동기화 방식으로 가장 많이 사용되는 것이 REST API, GRPC, GraphQL 같은 방법들이 존재하는데, 그중에서 가장 대표적인 REST API에 대해서 정리합니다.

REST API와 RESTful API는 약간 다릅니다. REST API는 서버가 가지고 있는 어떤 리소스에 대해서 표현할 수 있는 상태를 변경할 수 있는 하나의 표현 방법이라고 보면 됩니다.
그래서 이러한 표현 방법 중에서 데이터를 얻어오는 방법도 있고, 데이터 리소스의 상태를 변경하는 방법도 있습니다. 데이터 리소스를 추가하거나 삭제하는 방법도 여기에 포함됩니다. 이와 같이 데이터 리소스를 제어하는 방법을 API 형태로 제공하는 것을 REST API라고 합니다.

**RESTful API라는 것은 REST API를 만들기에 있어서 강력하게 규칙을 지켜야 한다는 것**이 RESTful API입니다.

리차든슨의 REST maturity 모델에 맞추어 REST API를 설계한다고 하면 강력한 규칙과 더불어서 시스템에서 필요로 하는 API 설계가 잘 만들어진다라고 보면 좋겠습니다.

**Level 0**
- REST 스타일의 웹 서비스를 처음 시작
	- 주소체계가 어떤 특별하게 의미를 담아서 만든 것이 아니라 필요에 따라서 즉석에서 만듭니다.
- http://server/getPosts
- http://server/deletePosts
- http://server/doThis

어떤 게시물을 저장하기 위해서 getPosts, deletePosts, doThis와 같이 이런식으로 해야 될 동작(get, delete, do)과 데이터(posts, this)를 한꺼번에 이름으로 표시하는 것이 레벨 0 단계입니다.

**Level 1**
- 적절한 URI을 가진 리소스를 노출하는 단계
- http://server/accounts
- http://server/accounts/10
- note: 현재 단계에서는 http 메서드를 사용하지 않는 단계

accounts 처럼 계정 정보를 위한 API 다음에 특별하게 10번이라는 계정을 특하도록 주소에 누구를 지칭하는 것인지 들어있습니다. 이게 레벨 1단계입니다.

Level 2
- Level 1 + HTTP Methods

레벨 1이 가지고 있는 특징에 HTTP 프로토콜의 메서드를 매핑하기 시작합니다. 예를 들어 글을 작성하기 위해서 POST 메서드 + post 와 같은 URI를 조합해서 할 수 있습니다.
글을 조회하기 위해서 GET 메서드 + post, 글을 수정하기 위해서 PUT 메서드 + post와 같이 조합할 수 있습니다.
이렇게 HTTP 메서드를 의미있게 데이터 리소스를 조작할때 사용하는 단계를 레벨 2입니다.

**Level 3**
- Level 2 + HATEOAS(헤테로스)
- DATA + NEXT POSSIBLE ACTIONS

HATEOAS 기능은 하이퍼링크 미디어라고 해서 웹사이트에서 어떤 링크를 클릭할 때 다른 사이트 다른 서비스로 이동 하는 것을 경험하신적이 있을 겁니다. 
실제로 웹브라우저로서 우리가 어떤 인터넷을 사용한다는 의미는 다양하게 링크를 통해 가지고 다른 사이트로 이동하는 것을 포함하고 있는데 바로 그렇게 API에다가 하이퍼미디어 텍스트처럼 링크를 통해 가지고 이동할 수 있는 기능까지 넣은 것을 하이퍼미디어, 즉 레벨 3이라고 봅니다.

이것이 중요한 부분은 사용자가 요청했던 데이터에 대한 응답을 받은 다음에 그 응답 값 안에는 단순한 결과만 들어있는 것이 아니라 다음에 어떤 동작을 할것인지 까지 포함하는 것이 우리는 Level 3라고 합니다.

다음에 어떤 동작을 할 수 있는지 포함되었다는 특징은 한번의 호출을 가지고 여러개의 해야될 동작을 알수 있기 때문에 네트워크 트래픽이 그만큼 감소될 수 있다는 특징을 가지고 있습니다.

![](../imgs/Pasted%20image%2020251023160931.png)
중간에 어떤 요청을 통해 가지고 다양하게 하이퍼링크를 가지고 어디로 이동할 수 있는지 이러한 정보가 한번의 요청에 의한 결과값으로 다 얻을 수 있습니다. 

그래서 궁극적으로 레벨 3까지 가는 것이 RESTful API에서 목표하고 있는 부분입니다.

RESTful API 설계시 유념해서 설계하면 좋은 부분
- Consumer first
	- API를 사용하고자 하는 쪽에 맞추어 API를 작성하세요
	- 개발자나 서비스를 제공하는 측면이 아닌 API를 사용할 수 있는 측면인 소비자 입장에서 어떻게 사용할 것인지 먼저 생각하고 설계하는 것이 필요합니다.
- Make best use of HTTP
	- HTTP의 특징을 사리세요.
- Request Methods
	- GET, POST, PUT, DELETE, PATCH
	- HTTP 메서드에서는 GET, POST, PUT, DELETE, PATCH와 같은 메서드들이 있는데 메서드 특징에 맞추어 리소스를 같이 접목해서 사용하면 적은 엔드포인트 주소를 가지고 다양한 기능을 수행할 수 있습니다.
- Response Status
	- 200, 201, 400, 401, 404
	- HTTP Response 수신시 응답 코드도 같이 받습니다. 응답 코드가 성공인지 오류인지 확인하기 위해서 REST API 설계시 HTTP Response에 응답 코드를 같이 넣어서 전달하도록 설계해야 합니다.
- No secure into in URI
	- 보안과 관련되어 있는 정보가 URI에 포함되면 안됩니다.
- Use plurals
	- 주소값 설계시 가능하면 복수 형태로 쓰는 것을 권장합니다.
	- `/users`, `/users/1`
- Use nouns for resources
	- 서버가 제공하려고 하는 어떤 데이터 리소스에 대해서 명사 형태로 쓰는 것이 더 직관적이다.
- For exceptions
	- 일관되게 접근 방식을 정의하세요.
		- /search
		- PUT /gists/{id}/star
		- DELETE /gists/{id}/star



## Spring Cloud란?
한 조사기관에 따르면 글로벌 애플리케이션 시장의 규모가 2024년에 25.64 billion(25억 6400만원)상당한 금액으로 커졌다고 평가를 하고 있습니다. 2025년부터 2030년까지 연평균 14.2% 상승할 것이라고 이야기 하고 있습니다.

https://spring.io/projects/spring-cloud
![](../imgs/Pasted%20image%2020251023164923.png)

현재 Spring Cloud 최신 버전은 2025.0.0 버전입니다. Spring Cloud는 하나의 단일 제품이 아닌 다양한 형태의 서브 프로젝트로 구성되어 있습니다. 이러한 서브 프로젝트들이 각각의 독립적인 버전을 가지고 있기 때문에 Spring Cloud 버전이 2025.0.0 버전이라고 명시했지만 어떤 서비스는 다른 버전을 가지고 있을 수 있습니다.

![](../imgs/Pasted%20image%2020251023170103.png)
그래서 Spring Cloud에서는 버전의 관리를 Release Train이라는 이름으로 표시하는 경우가 있습니다. 예를 들어 2025.0.x aka Northfields 등이 있습니다. 이 이름을 살펴보면 Spring Cloud안에 포함되어 있는 서브 프로젝트들이 어떤 버전으로 그룹핑 되어 있는지 확인할 수 있습니다.

Spring Cloud 특징

- Service discovery
- Circuit breakers
	- 마이크로서비스 환경에서 서비스간 통신 실패시 안정적으로 처리하기 위한 패턴
- Intelligent routing
- Micro-proxy
- Control-bus
- Short lived microservices and contact testing

우리는 Release Trains을 통해서 Spring Cloud 버전을 확인할 수 있는데 이것이 중요한 이유는 Spring Cloud만 가지고 독립적인 애플리케이션을 만들 수 없기 때문입니다. 반드시 Spring Boot를 이용해서 Spring 기반 애플리케이션 비즈니스 로직을 가지고 있는 애플리케이션과 비즈니스 로직의 서비스를 실행하는 환경에서 실행될 수 있는 Spring Cloud에서 애기하는 오케스트레이션 아키텍처를 어떻게 지원하는지를 같이 확인해주셔야 합니다. 이때 Spring Boot 버전과 Spring Cloud 버전을 서로 매칭해 가면서 개발해야 합니다.

예를 들어 Spring Boot 3.5.x 버전을 사용시 Northfields라고 알려진 2025.0.x 버전을 사용해야 합니다.

	- Hystrix

### Spring Cloud vs Kubernetes
Spring Cloud와 Kubernetes는 비슷한 영역도 있지만 전혀 다른 영역도 있기 때문에 이것은 비교 대상이라기보다는 각각 좋은 점과 필요한 점을 선택해서 개발하는게 좋습니다.

넷플릭스 초창기 구성도를 보면 클라이언트가 먼저 정보를 요청하게 되면 API 게이트웨이 역할을 하는 게 당시에 ZUUL 이라는 게이트웨이에서 클라이언트 요청을 받은 다음에 어디로 갈지 분배합니다. 

![MSA with Spring Cloud (by A. Lukyanchikov)](../imgs/Pasted%20image%2020251024124504.png)
예를 들어서 Statistics Service, Account Service, Notification Service가 있다고 가정할때 각각의 마이크로 서비스에서 Ribbon과 같은 로드밸런서 역할을 하는 부분과 회복성 체크를 해줄수 있는 Hystrix 같은 제품이 포함되어 있습니다. 이러한 Ribbon, Hystrix와 같은 제품들이 Eureka라고 되어 있는 서비스 디스커버리에 등록이 되고 검색이 되는 구조입니다. 

환경 설정 구성 정보를 위해서 외부에 있는 Config Service를 토통해서 Configuration 정보를 사용합니다. 
Auth Service를 통하여 인증에 대한 정보를 더 사용하고 모니터링이나 로그 분석을 위해서 ELK Stack 이나 Turbin와 같은 서비스 제품을 사용합니다.

위 그림에서 중앙에 있는 서비스 3가지가 Inner Architecture에 속합니다.

API Gateway, Service Discovery, 모니터링 도구, 로그 분석 도구, 설정 서비스 도구, 인증 서비스들은 Outer Architecture에 해당됩니다.

**Microservices Concerns**
- Config Management
- Service Discovery & Load Balancing
- Resilience & Fault Tolerance
- API Management
- Service Security
- Centralized Logging
- Centralized Metrics
- Distributed Tracing
- Scheduling & Deployment
- Auto Scaling & Self Healing

Spring Cloud에서도 위와 같은 기능을 제공하고 쿠버네티스에서도 이런 부분을 제공하고 있습니다.

![](../imgs/Pasted%20image%2020251024124538.png)
Spring Cloud에서 제공하는 기능은 초록색으로 표시하고, Kubernetes에서 제공되는 제품을 파란색으로 제공됩니다.

![](../imgs/Pasted%20image%2020251024124549.png)
위 그림에서 예를 들어 Auto Scaling & Self Healing 기능 같은 경우에는 쿠버네티스에서는 Pod/Cluster Autoscaler 또는 Scheduler라는 기능이 제공됩니다.

Distributed Tracing, Centralized Metrics, Centralized Logging 기능 같은 경우에는 Spring Cloud, 쿠버네티스 모두 지원하지 않습니다. 대신에 Zipkin, Prometheus, EFK 제품을 사용해야 합니다.

Outher Architecture에 필요한 부분 서비스 디스커버리라든가 게이트웨이에 관련된 부분이 있다라고 하면 Spring Cloud의 기능 일부와 쿠버네티스에 있는 기능을 이용해서 적절하게 조합해서 운영하는게 일반적인 방법입니다.
