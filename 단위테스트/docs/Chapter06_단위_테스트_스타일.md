
## 6.2 단위 테스트 스타일 비교
4대 요소(회귀 방지, 리팩토링 내성, 빠른 피드백, 유지 보수성)를 통한 단위 테스트 스타일을 비교한다.

### 6.2.1 회귀 방지와 피드백 속도 지표로 스타일 비교하기
회귀 방지와 피드백 속도 측면에서 3가지 스타일을 비교해본다.

**회귀 방지 측면**
- 회귀 방지는 프로덕션 코드를 수정할때 테스트가 얼마나 실제 버그를 잘 잡아내는지 나타내는 지표
- 단위 테스트의 3가지 스타일(출력 기반, 상태 기반, 통신 기반)을 사용한다고 해서 회귀 방지 지표에 영향을 미치지 않는다.

**빠른 피드백 측면**
- 빠른 피드백은 테스트를 빠르게 실행해서 개발자에게 얼마나 빠르게 결과를 보여주는지 알려주는 지표
- 단위 테스트의 3가지 스타일 모두 피드백 속도에 영향을 미치지 않는다.
- 통신 기반 스타일 같은 경우에 Mocking을 하게 되면 런타임 시점에 지연 시간을 주지만, 수만개의 수준이 아니라면 별로 차이가 없어서 비슷하다.

### 6.2.2 리팩토링 내성 지표로 스타일 비교하기
**출력 기반 테스트**
- 리팩토링 내성 높음
- 출력 기반 테스트는 내부 구현 사항과 결합되어 있지 않기 때문에 리팩토링 내성이 높다

**상태 기반 테스트**
- 리팩토링 내성 보통
- 구현 세부 사항과 결합될 가능성이 높아서 거짓 양성 발생이 쉽다.

**통신 기반 테스트**
- 리팩토링 내성 가장 낮음
- 상호작용 검증 및 구현 세부사항과 관계가 깊어서 거짓 양성 발생 가능성이 높다.

### 6.2.3 유지 보수성 지표로 스타일 비교하기
**출력 기반 테스트**
- 유지 보수성 최상
- 입력 및 출력 검증만 신경쓰면 되기 때문이다.

**상태 기반 테스트**
- 출력 기반보다 상대적으로 유지 보수성 낮다.
- 출력 검증보다 더 많은 상태 검증을 테스트 코드로 추가해야 한다.
- 상태 기반으로 검증하기 위해서 헬퍼 메서드나 동등성 검증을 통한 방법이 존재하지만 출력 기반 테스트보다 공간을 더 많이 차지하고 유지보수성이 떨어지게 된다.

**통신 기반 테스트**
- 유지 보수성 낮음
- 테스트 대역과 상호작용 검증을 설정해야 되서 공간을 많이 차지하게 된다.
- 목이 사슬 형태로 되어 있는 경우 테스트가 커지고 유지보수가 어려워진다.

### 6.2.4 스타일 비교하기: 결론

단위 테스트 스타일 비교

|                        | 출력 기반 | 상태 기반 | 통신 기반 |
| ---------------------- | ----- | ----- | ----- |
| 회귀 방지 및 피드백 속도         | 동일    | 동일    | 동일    |
| 리팩토링 내성을 지키기 위한 필요한 노력 | 낮음    | 중간    | 중간    |
| 유지보수성 비용               | 낮음    | 중간    | 높음    |

결론
- 왠만하면 출력 기반 테스트를 기반으로 테스트를 구현하라.
- 코드를 순수 함수로 만들면 상태 기반 테스트나 통신 기반 테스트 대신 출력 기반 테스트로 변환이 가능하다.

## 6.3 함수형 아키텍처 이해
상태 기반 테스트나 통신 기반 테스트를 순수 함수로 만들어 출력 기반 테스트로 변환하기 위해서는 함수형 프로그래밍과 함수형 아키텍처가 무엇인지 알아야 한다. 6.4 절에서는 예제를 통해서 바꾸는 방법을 설명하고 있다.

6.3 절에서는 함수형 프로그래밍과 함수형 아키텍처가 무엇인지 설명한다.

### 6.3.1 함수형 프로그래밍이란?
함수형 프로그래밍은 메서드를 호출할때 호출 횟수 상관없이 동일한 입력에 대해서 동일한 출력이 발생해야 하는 함수이다.
함수형 프로그래밍을 적용한 메서드는 메서드 시그니처(매개변수, 리턴타입)에 입력과 출력이 모두 명세되어 있어야 한다.

메서드 호출시 숨은 입출력이 발생하면 테스트를 검증하기 어려워진다. 예를 들어 다음과 같은 사례가 있다.
- 사이드 이펙트
	- 인스턴스 상태 변경, 파일 업데이트 등
- 예외
	- 예외가 발생해서 우회 경로를 만들게 된다.
- 내외부 상태에 대한 참조
	- LocalDateTime.now와 같이 정적 메서드를 사용해서 현재 날짜와 시간을 가져오는 메서드가 있을 수 있다.
	- 데이터베이스 질의
	- 비공개 변경 가능 필드를 참조하는 경우

참조 투명성
- 메서드에 대한 호출하고 나온 반환값을 대체할 수 있는 것
- 예를 들어 `increment(4)`에 대한 메서드 호출을 상수 `5`로 대체 할 수 있다면, 해당 메서드는 참조 투명성을 가진다.

함수형 프로그래밍이 아닌 경우
- x값이 사이드 이펙트
```java
int x = 0;
public int increment(){
	x++;
	return x;
}
```

- `comments.add(newComment)` 메서드 호출이 사이드 이펙트
```java
public Comment addComment(String text, String author, LocalDateTime dateCreated) {  
    Comment newComment = new Comment(text, author, dateCreated);  
    comments.add(newComment); // 사이드 이펙트  
    return newComment;  
}
```

### 6.3.2 함수형 아키텍처란?
사이드 이펙트를 일으키지 않는 애플리케이션은 만들 수는 없다. 사용자 정보 업데이트, 장바구니에 주문 추가 등 모든 애플리케이션이 사이드 이펙트를 만들어낸다.

함수형 프로그래밍 목표
- 사이드 이펙트 완전 제거가 아니다.
- **비즈니스 로직을 처리하는 코드와 사이드 이펙트를 일으키는 코드를 분리하자**
- 사이드 이펙트를 비즈니스 연산 끝으로 몰아서 비즈니스 로직을 사이드 이펙트와 분리한다.

다음은 두가지 코드 유형을 구분해서 비즈니스 로직과 사이드 이펙트를 분리할 수 있다.
- **결정을 내리는 코드** : 이 코드는 사이드 이펙트가 필요 없기 때문에 수학적 함수를 사용해 작성할 수 있다.
	- 결정을 내리는 코드를 **함수형 코어** 또는 불변 코어라고 함
- **해당 결정에 따라 작용하는 코드** : 이 코드는 수학적 함수에 의해 이루어진 모든 결정을 데이터베이스의 변경이나 메시지 버스로 전송된 메시지와 같이 가시적인 부분으로 변환한다.
	- 해당 결정에 따라 작용하는 코드를 **가변 셸이**라고 한다.

함수형 코어와 가변 셸 협력 방식
- 가변 셸은 모든 입력을 수집한다.
- 함수형 코어는 결정을 생성한다.
- 셸은 결정을 사이드 이펙트로 변환한다.

목표는 출력 기반 테스트로 함수형 코어를 두루 다루고, 가변 셸을 훨씬 더 적은 수의 통합 테스트에 맡긴다.

### 6.3.3 함수형 아키텍처와 육각형 아키텍처 비교

의존성 차이
- 육각형 아키텍처는 도메인 계층은 서비스 계층에게 의존하면 안된다.
- 함수형 아키텍처는 함수형 코어는 가변 셸에게 의존하면 안된다.

사이드 이펙트 차이
- 육각형 아키텍처는 모든 수정 사항은 도메인 계층 내에 있어야 하며, 계층간 경계를 넘어가서는 안된다.
- 함수형 아키텍처는 가변셸이 처리해야 한다.

함수형 아키텍처는 육각형 아키텍처의 하위 집합이다.
